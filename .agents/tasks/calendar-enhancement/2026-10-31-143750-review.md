**Verdict**: APPROVED

Premium calendar components for resident timeline and PG-wide events with Apple design aesthetics. Both ResidentCalendar and DashboardCalendar deliver compact, interactive UIs with glassmorphism, hover tooltips, click panels, mobile swipe navigation, and proper TypeScript safety patterns.

## Server action data queries and type safety

lib/services/dashboard-calendar.ts implements `getDashboardCalendarData(month: string)` server action marked with 'use server' directive. Imports all models at top: Resident, Room, Bed, Plan, RentRecord, Payment, ElectricityBill, Deposit, PlanHistory, Settings. Critical pattern implemented at lines 15-24:

```typescript
// Ensure models are registered with Mongoose before populate() is used.
// The imports are referenced here to prevent tree-shaking by Turbopack.
void Room;
void Bed;
void Plan;
void RentRecord;
void Payment;
void ElectricityBill;
void Deposit;
void PlanHistory;
void Settings;
```

This void Model pattern prevents MissingSchemaError by forcing Turbopack to include model files even when not directly referenced. Without this, Mongoose populate() fails with "Schema hasn't been registered for model 'X'" error. Pattern correctly applied in both dashboard-calendar.ts and residents.ts (lines 17-21 in residents.ts for Room, Bed, Plan models used in populate()).

getDashboardCalendarData queries 6 event types for given month:

1. **paymentsData**: Payment.find({ paymentDate: { $gte: startDate, $lte: endDate } }).lean() grouped by date with count and totalAmount aggregation, populates resident name
2. **rentDueData**: RentRecord.find({ dueDate in month, status: 'pending' | 'partial' }).populate('resident', 'name').lean() grouped by date
3. **checkoutsData**: Resident.find({ expectedLeavingDate or leavingDate in month }).populate('room').lean() grouped by date
4. **checkinsData**: Resident.find({ joiningDate in month }).lean() grouped by date
5. **noticesData**: Resident.find({ noticeDate in month }).lean() grouped by date
6. **depositRefundsData**: (not currently queried, placeholder for future)

All queries use .lean() to return plain JavaScript objects (not Mongoose documents) ensuring JSON serializability for client components. Date fields converted to ISO strings via .toISOString(). Return type DashboardCalendarData exported as TypeScript interface with proper nested types for PaymentDayData, RentDueDayData, CheckoutDayData, etc.

heatmapData calculated by iterating date range and summing activity scores: `(paymentCount * 10) + (checkoutCount * 15) + (checkinCount * 15) + (rentDueCount * 8)`. Weights chosen to emphasize check-in/checkout events (15 points each, highest impact) over rent dues (8 points) and payments (10 points). Zero scores included for all dates to ensure complete month coverage in heatmap view.

todaySummary aggregates today's events only: counts and amounts for payments expected, check-ins scheduled, check-outs expected, rent dues today. Used for top stats bar display and filter initialization.

lib/services/residents.ts implements getResidentCalendarData(residentId: string) for ResidentCalendar. Similar void Model pattern at lines 17-21 prevents populate() errors. Returns ResidentCalendarData interface with events array (discriminated union type), pendingRentRanges, totalPendingAmount, totalPendingElectricity, nextDueDate, daysStayed. Events include joining, rent_due, payment, plan_change, electricity, notice, leaving types with type-specific data fields.

## Type safety and code quality

ResidentCalendar.tsx has strong type safety: props interface explicitly types ResidentData, PlanHistoryData with proper field types. CalendarEvent imported from server action, transformed to ClientCalendarEvent with Date objects instead of ISO strings. No 'any' types in ResidentCalendar component logic, all map/filter callbacks properly typed.

DashboardCalendar.tsx has minor type safety gaps: eventsByDate Map typed as `Map<string, Array<{ type: string; color: string; count: number; data: any }>>` at lines 79 and 152. The `data: any` field bypasses compile-time checks for PaymentDayData vs RentDueDayData vs CheckoutDayData union. Proper fix: create EventMapEntry type with discriminated union matching server data types.

Sheet detail rendering uses inline `(p: any)`, `(r: any)` for nested arrays at lines 717, 735, 753, 769, 785. Example line 717: `{event.data.payments.map((p: any, i: number) =>`. Should be typed as PaymentDayData['payments'][number] which has residentId, residentName, amount, method fields. TypeScript compilation succeeds despite 'any' types, but loses autocomplete and refactor safety for these nested data accesses.

agendaDays useMemo at line 197 uses `Array<{ date: Date; dateKey: string; events: any[] }>`. Should type events as EventMapEntry[] or similar. Build succeeds with no errors confirming type issues are non-blocking.

Both components follow React best practices: useState for local UI state, useMemo for derived data/expensive computations, proper key props in .map() calls, event handlers with descriptive names. No useEffect dependencies warnings, no infinite render loops.

## Mobile responsiveness implementation

Both components use Tailwind responsive prefixes for mobile-first design. Summary stats use `grid grid-cols-2 lg:grid-cols-4` ensuring 2-column layout on mobile, 4-column on desktop. Stat cards readable on 320px viewports with text-[10px] labels and text-2xl values wrapping properly.

ResidentCalendar week/month toggle wrapped in `<div className="lg:hidden">` making it visible only on screens below 1024px. Desktop users see full month view only. Toggle buttons styled with active state indicators, clicking updates viewMode state which filters displayDays from 42 to 7 dates. Week view shows current week (Sunday through Saturday) calculated from today's date.

DashboardCalendar stats bar uses same 2-column mobile pattern. View mode toggle (Grid/Heatmap/Agenda) does not have lg:hidden, remains visible on all screen sizes since desktop users may want heatmap or agenda views. Buttons wrap or scroll horizontally on narrow screens via flex layout.

Sheet components use `w-[90vw] sm:max-w-md` ensuring they don't overflow on mobile (90% viewport width) while capping at 448px on tablets/desktop. DashboardCalendar adds `lg:w-[400px]` for fixed width on large screens. side="right" on desktop provides right-side slide-in, mobile defaults to bottom or adapts based on screen size (shadcn/ui Sheet component behavior).

Calendar grid always uses grid-cols-7 (7 days) but cells shrink naturally on narrow screens. aspect-square maintains square date cells, p-1.5 keeps them tappable on touch screens (minimum 44x44px iOS guideline met with padding). Text-sm date numbers remain readable at small sizes.

Swipe navigation (ResidentCalendar only) uses native touch events with 50px threshold, provides gesture-friendly month navigation on mobile without relying on small arrow buttons. Desktop users use ChevronLeft/Right buttons. Both input methods functional across devices.
